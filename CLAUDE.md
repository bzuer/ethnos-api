# Ethnos_API — Project Instructions

Academic bibliographic system API built with Node.js/Express, backed by MariaDB. Full-text search for `works` and `persons` runs against a **Manticore Search** daemon (SphinxQL on `127.0.0.1:9306`) that indexes straight from the base tables; `venues`, `subjects`, and `organizations` use their own MariaDB FULLTEXT indexes. Manticore is not a separate endpoint — it powers `/works`, `/publications`, `/search/*`, `/persons`, and autocomplete. The backend is selected by `SEARCH_BACKEND` (`manticore` | `mariadb`); the runtime pins `manticore`, which is mandatory for works (the MariaDB works FULLTEXT surface no longer exists).

## Runtime and Execution
- Runtime: Node.js (>= 24). Framework: Express 5. Entry points: `src/app.js` (HTTP), `src/https-app.js` (HTTPS).
- Express 5 request-handling contract (do not regress):
  - The catch-all 404 is mounted path-less as `app.use(notFoundHandler)`. The Express 4 string wildcard `app.use('*', ...)` throws at boot under path-to-regexp v8.
  - `req.query` is a getter-only accessor. The early query middleware in `src/app.js` publishes the parsed object via `Object.defineProperty(req, 'query', { writable: true, ... })`; a bare `req.query = ...` assignment is a silent no-op and drops every param.
  - Keep `query parser` set to `false` — the middleware owns parsing, so `src/middleware/sanitization.js` (reassigns `req.query`) and `src/middleware/pagination.js` (mutates `req.query.page/limit/offset`) keep working.
- Runtime env: `/etc/node-backend.env` is the single source of truth. Never version secrets or credentials.
- API runtime port: `1211` (production and development).
- Test ports: `3000` is the in-process default when `NODE_ENV=test`; integration tests target `1210` via `INTEGRATION_BASE_URL`, so a temporary instance on `PORT=1210` is the expected target. Never touch the live `1211` when validating changes.
- Development: `npm run dev`. Build: `npm run build`. Production: systemd user service `ethnos-api.service` via `systemctl --user`; `server.sh` is the legacy fallback (PM2/nohup).
- Systemd setup: `scripts/manage.sh systemd:install` installs the user unit to `~/.config/systemd/user/`. No sudo required.

## Database
- **Strict consumer-only.** This project NEVER creates, executes, or alters database procedures, events, triggers, indexes, table structures, or row data. It only issues read-side `SELECT` / `EXISTS` queries. The API issues no `CALL`. Any structural change (DDL, `CREATE`/`ALTER`/`DROP`, `INSERT`/`UPDATE`/`DELETE`, `CALL`, `TRUNCATE`) is performed by a separate operations pipeline. Read-only utilities (`mysqldump -d`, `SELECT … FROM information_schema.*`) are allowed.
- **Schema snapshots.** The current schema lives under `backups/` as a dated dump, `backups/data.schema.YYYY-MM-DD.sql`, generated by `scripts/maintenance/publications/regenerate_schema_dump.sh` (which runs `mysqldump -d --routines --events --order-by-primary --single-transaction --compact --skip-comments --skip-tz-utc --default-character-set=utf8mb4 data`). Any API change must be written against — and any DB change must be reflected in — the latest snapshot.
- **Operator DDL the API needs** goes in the single file `database/required_objects.sql`: objects to create (things the API depends on that do not exist yet) and redundant/dead objects to drop. The operator applies it, regenerates the snapshot, and the API is then updated to consult it. Keep it idempotent and empty out entries once applied.
- Database name: `data`. Direct access: `mariadb data` or `mariadb data -e "..."`.
- Topology: **28 base tables, 0 views, 4 functions, 53 stored procedures, 5 triggers.** A work is a *multi-manifestation* record: work type is per-publication on `publications.type`, so one work can carry publications of different types (e.g. a PREPRINT and an ARTICLE). The API surfaces a work's displayed type from its primary/latest publication and filters `type` with `any_publication` semantics (a work matches if any of its publications is of that type).

### Base-table architecture
Six core tables carry the read path:
- `works` — the parent of search. Columns: `title`, `subtitle`, the generated `full_title_normalized` (lower-cased title + subtitle, capped at 255, indexed by the plain B-tree `idx_works_full_title_normalized`), `abstract`, `language`, `citation_count` (incoming), `reference_count` (outgoing), `download_count`, `view_count`, `altmetric_score`, `social_media_mentions`, `news_mentions`, the per-work `latest_publication_year` (MAX of the work's `publications.year`, maintained by `sp_refresh_works_publication_years` and indexed by `idx_works_latest_pub_year` to back the `publication_year` sort; a work's earliest year, needed only on the detail endpoint, is derived on the fly as MIN over its hydrated publications), `created_at`, `updated_at`, `metrics_last_updated`. Other indexes cover `citation_count DESC`, `reference_count` (`idx_works_reference_count`, backs the indexed `sort_by=references_count`), `metrics_last_updated`, `language`, `created_at`, `updated_at`. `works` has **no** FULLTEXT index and **no** per-work type or search-text columns — full-text is served by Manticore.
- `publications` — one row per published instance of a work. Columns: `work_id`, `venue_id`, `publisher_id`, `type` (`ARTICLE|BOOK|CHAPTER|THESIS|CONFERENCE|CONFERENCE_PAPER|REPORT|DATASET|PREPRINT|REVIEW|EDITORIAL|OTHER`, indexed by `idx_publications_type`), `doi (UQ)`, `publication_date`, the generated `year`, `volume`, `issue`, `pages`, `open_access`, `peer_reviewed`, `source` plus the provenance columns `source_prefix`/`source_member_id`/`source_content_domain` (JSON)/`source_indexed_at`/`source_deposited_at`, `license_url`, `license_version`, `external_ids` (JSON), the unique `bibtex_key`, and 19 identifier columns (`isbn`, `arxiv`, `pmid`, `pmcid`, `wos_id`, `handle`, `wikidata_id`, `openalex_id`, `scielo_pid`, `openlibrary_id`, `asin`, `google_book_id`, `mag_id`, `ddc`, `lcc`, `udc`, `lbc`, `oclc`, `lccn`) — most under UNIQUE constraints. Listing predicates are covered by `idx_publications_work_year_id`, `idx_publications_venue_year_oa`, `idx_publications_publisher_year`, `idx_publications_year`, `idx_publications_type`, `idx_publications_oclc`, `idx_publications_lccn`.
- `venues` — the venue-level entity. Owns `name`, `abbreviated_name`, `type` (`JOURNAL|CONFERENCE|REPOSITORY|BOOK_SERIES|SOURCE_BOOK|OTHER`), `publisher_id`, `country_code`, `lang`, `issn`, `eissn`, `isbn13`, `homepage_url`, `aggregation_type`, `open_access`, `is_in_doaj`, `is_in_scielo`, `is_indexed_in_scopus`, `cited_by_count`, `impact_factor`, `citescore`, `sjr`, `snip`, `h_index`, `i10_index`, `2yr_mean_citedness`, `coverage_start_year`, `coverage_end_year`, the identifier surface (`scopus_id`, `wikidata_id`, `openalex_id`, `scielo_id`, `openlibrary_work`), the ranking columns (`total_score` = `subject_score` + `oa_score` + `impact_score` + `llm_score`, plus `llm_relevance`/`llm_justification`; `impact_score` is a blended bibliometric impact signal; `authorship_score`/`affiliation_score`/`citation_score` are additional operator-side inputs consumed by `sp_calculate_venue_ranking` — held at 0 today but **required by the internal ranking calculation**, so never drop them; the API does not expose them), the `validation_status`/`last_validated_at` audit pair, and the generated virtual `name_dedup_key`. `FULLTEXT ft_venues_search (name, abbreviated_name)` covers venue lookups.
- `persons` — the researcher entity. Owns `preferred_name`, `family_name`, `given_names`, `signature_id`, `orcid`, `scopus_id`, `lattes_id`, the metric block (`total_works`, `total_citations`, `h_index`, `first_publication_year`, `latest_publication_year`, `corresponding_author_count`, `is_verified`), the generated `normalized_name`, plus `FULLTEXT ft_persons_names (preferred_name, given_names, family_name)`.
- `subjects` — controlled-vocabulary terms. Owns `term`, `vocabulary` (default `Keyword`), `subject_type`, `lang`, the multilingual `term_pt`/`term_es`, `external_id`, a self-referential `parent_id` (term hierarchy), `term_key`, the operator-maintained denormalized `total_works` (INT = `COUNT(DISTINCT work_id)` over `work_subjects` for that subject, indexed by `idx_subjects_total_works`, refreshed by `sp_refresh_subjects_total_works_simple`), and the generated dedup columns `normalized_term`/`subject_type_nn`/`dedup_key`. `FULLTEXT ft_subjects_term (term)` drives free-text term search.
- `organizations` — institutions, publishers, funders, companies. Typed by `type` (`UNIVERSITY|INSTITUTE|PUBLISHER|FUNDER|COMPANY|OTHER`) plus the finer `openalex_type` and a lifecycle `status` (active/inactive/withdrawn). Owns the identifier surface (`ror_id`, `grid_id`, `wikidata_id`, `openalex_id`, `mag_id`, `url`), the JSON name arrays `acronyms` / `alternative_names`, the generated `standardized_name`, and operator-maintained metric columns the API reads verbatim: `publication_count` (local works), `researcher_count` (local distinct affiliated authors), `total_citations`, `h_index`, `i10_index`, `2yr_mean_citedness`, `open_access_works_count`. `FULLTEXT ft_organizations_name (name)` plus an exact match against the `acronyms` JSON array drive institution lookups (e.g. `USP` → the canonical org). The operator-side columns `unresolved_reason` (`SUBENTITY|COMPOUND|OTHER`), `cluster_key`, and `semantic_key` exist but the API never reads them.

Relations the read path joins through: `authorships` (`affiliation_id`, authorship → `persons`), `work_references`, `work_subjects` (→ `subjects`), `venue_subjects` (→ `subjects`), `files` (keyed by `publication_id`), `signatures` (via `persons.signature_id`), `organization_relationships` (org hierarchy), `funding` (`work_id` → `funder_id` with `grant_number`). The course domain is `courses` / `course_bibliography` / `course_instructors`; `programs` (degree programs by institution) exists but is currently empty.

Operator-side tables the API never reads: `multi_manifestation_works` (multi-manifestation markers), `venue_merge_map` / `venue_merge_audit` (venue dedup), `pub_isbn13_map` / `venue_isbn13_map` (ISBN-13 maps driving the book-manifestation collapse), `publication_relevance` (per-publication `score`/`rel_class`), `subject_relevance_tiers` / `subject_stoplist` / `venue_ranking_rules` (relevance and ranking inputs), `persons_quarantine_orgs` (quarantined person rows).

### Operator-side maintenance
- The operator pipeline owns every write and keeps the metric columns on `works`/`persons`/`venues`/`organizations`/`subjects` current (`sp_update_*`, `sp_refresh_persons_stats`, `sp_refresh_subjects_total_works_simple`, `sp_compute_publication_relevance`, `sp_calculate_venue_ranking`, the references-consistency procedures, etc.). The API calls none of them.
- Works/persons full-text is served entirely by Manticore, rebuilt operator-side via `scripts/manticore/reindex.sh`. The base-table FULLTEXT indexes (`ft_venues_search`, `ft_persons_names`, `ft_subjects_term`, `ft_organizations_name`) update in place with their rows.
- The `summary_*` denormalized layer and the Sphinx runtime do not exist as tables; do not reintroduce them. (The operator keeps a dormant `sp_build_summary_venues` procedure, but it materializes no persistent table and the API never calls it.)

### Schema contracts on the read path
- Citations / references: use the unified `work_references` table (`status`: `PENDING|RESOLVED|FAILED`). `RESOLVED` means the cited work exists in DB; `PENDING` means it does not yet (expected state, not an error).
- Person-signature relation: direct via `persons.signature_id`.
- Publication-file relation: direct in `files` via `publication_id` (`file_role` distinguishes roles). There is no work-level file column — join through `publications.work_id` when a work-scoped file query is needed.
- Work-level metric columns: `works.citation_count`, `works.reference_count`, `works.download_count`, `works.view_count`, `works.altmetric_score`, `works.social_media_mentions`, `works.news_mentions`.
- Per-publication hydration: authors/subjects/files are derived with follow-up JOINs — authors via `authorships INNER JOIN persons`, subjects via `work_subjects INNER JOIN subjects`, files via `files` keyed by `publication_id`. There are no `authors_json` / `subjects_json` / `files_json` cache columns.

## Response Conventions
- All responses flow through `responseFormatter` (global in `src/app.js`) and `src/utils/responseBuilder.js`.
- Success envelope: `{ status: 'success', data, pagination?, meta? }`.
- Error envelope: `{ status: 'error', message, code, timestamp, meta? }`.
- Errors are raised via `res.fail(...)` and `res.error(err, ...)` with `ERROR_CODES`.
- Pagination is mandatory for listings. Use `createPagination` / `normalizePagination` from `src/utils/pagination.js`. Both `page/limit` and `offset/limit` are accepted simultaneously.
- On JOIN-heavy listings (`/works`, `/search/works`, `/publications`), `pagination.total` is best-effort: the count uses a 2 s server-side budget (`SET STATEMENT max_statement_time`). When the budget fires, the response falls back to an estimate and sets `meta.pagination_total_exact = false`. Clients needing an exact count must detect that flag (and/or rely on the `data.length < limit` terminator on the last page).
- **Statement-budget discipline (do not re-invert).** Every heavy read is bounded *below* the request ceiling so a slow query is killed and degrades gracefully instead of 503-ing. `src/utils/db.js` derives `DEFAULT_MS = max(1000, min(DB_QUERY_TIMEOUT_MS, REQUEST_TIMEOUT_MS - headroom))` — always under `REQUEST_TIMEOUT_MS` (default 5 s) — and `withTimeout(sql, ms)` clamps any caller-supplied budget to that ceiling. Overruns raise a statement-timeout error (detected by `isStatementTimeout`) that services catch to serve a bounded fallback. Never pass a per-query budget above `REQUEST_TIMEOUT_MS`, and never let the request timeout fire before the query budget — that re-inverts the relationship and re-breaks graceful degradation.

## Security and Internal Access
- **The API is open by default — no key required.** Every data and metrics endpoint (`/`, `/works`, `/publications`, `/persons`, `/venues`, `/institutions`, `/search/*`, `/subjects`, `/signatures`, `/courses`, `/instructors`, `/bibliographies`, `/metrics/*`, citations, collaborations, the DOI resolver regex) is reachable without any header. Unauthenticated traffic is governed by the rate limiter.
- **Endpoints that require `X-Access-Key`** keep their own per-route guard: `/dashboard/*` and the internal health probes `/health/readiness` + `/health/metrics` use `requireInternalAccessKey`; `/security/*` uses a dedicated `createAccessKeyGuard`. These reject with 401 when the key is missing or invalid. `/health/liveness`, `/docs*`, and the OpenAPI documents stay public.
- **The key is an optional rate-limit bypass on the open endpoints.** Header aliases (case-insensitive): `x-access-key`, `x-internal-key`, `x-api-key`. Query-string aliases: `access_key`, `accessKey`, `api_key`. Any accepted value lifts the per-minute cap for that request.
- **Rate limiting is enabled by default** (`RATE_LIMIT_DISABLED` defaults to `false`). Unauthenticated requests are capped at `RATE_LIMIT_GENERAL` (default **120/min per IP**, window `RATE_LIMIT_WINDOW_MS`, default 60s) across `generalLimiter` / `searchLimiter` / `metricsLimiter` / `relationalLimiter` / `speedLimiter`; requests over the cap get 429. `shouldSkipRateLimit` in `src/middleware/rateLimiting.js` exempts localhost (`isLocalRequest`) and any request carrying a valid key (`hasValidAccessKey`).
- **Multiple keys are accepted.** `requireInternalAccessKey` / `hasValidAccessKey` collect values from every configured env var and accept any match: `API_KEY`, `INTERNAL_ACCESS_KEY`, `SECURITY_ACCESS_KEY`, `API_ACCESS_KEY`, `ETHNOS_API_KEY`, `ETHNOS_API_ACCESS_KEY`, `API_SECRET_KEY`, `ETHNOS_API_KEY_2`. Add keys by setting additional env vars on the same list.
- Middleware: `src/middleware/accessKey.js` exports `requireInternalAccessKey`, `createAccessKeyGuard`, `hasValidAccessKey`, `DEFAULT_ACCEPTED_ENV_VARS`.
- OpenAPI declares `securitySchemes.XAccessKey` and applies it globally as **optional** via `security: [{}, { XAccessKey: [] }]`. Gated operations (`/dashboard/*`, `/security/*`, `/health/readiness`, `/health/metrics`) override per-operation with `security: [{ XAccessKey: [] }]`; `/health/liveness` opts out with `security: []`.
- Do not expose keys or sensitive data in responses, logs, or error payloads.

## Route Standards
- Plural collections: `/bibliographies`, `/institutions`, `/publications`, `/works`, `/persons`, `/venues`, `/courses`, `/instructors`, `/subjects`, `/signatures`.
- Health probes: `/health/liveness`, `/health/readiness`, `/health/metrics`.
- Venue payloads expose `abbreviated_name` alongside `name` (or `venue_abbreviated_name` alongside `venue_name`). Both must appear together when either is exposed.
- All optional query params use `optional({ values: 'falsy' })` so empty strings (`param=`) are treated as absent. Controllers normalize empty-string params to `undefined` before passing to services (never treat `""` as `false` for booleans).

### Citation filters on work/publication listings
- Every listing that surfaces works or publications accepts `cited_by_min`, `cited_by_max`, `sort_by`, `sort_order` on top of endpoint-specific filters. The aliases `citation_count_min` / `citation_count_max` (and `sortBy` / `sortOrder`) are also honoured.
- `cited_by_min` / `cited_by_max` are inclusive bounds against `works.citation_count`. Empty or invalid values are ignored.
- `sort_by` accepts `cited_by_count`, `references_count`, `publication_year`, `id`, and — where applicable — `relevance`. `sort_order` defaults to `DESC` for numeric fields and accepts `ASC` / `DESC`. With `sort_by` omitted: `publication_year DESC, id DESC` on DB-backed listings, relevance on full-text paths.
- Endpoints: `/works`, `/works/showcase`, `/publications`, `/search/works`, `/search/advanced`, `/persons/{id}/works`, `/venues/{id}/works`. All translate the citation bounds to `w.citation_count >= ?` / `<= ?` against `works`.
- List items expose `cited_by_count` and `references_count` (work listings) or `citation_count` / `reference_count` (publication listings); `/persons/{id}/works` and `/venues/{id}/works` join `works` so `cited_by_count` surfaces on every row.

### Works endpoints
- Listings: `/works`, `/works/showcase`, `/search/works`, `/search/advanced`. Filters apply with `meta.match_mode = "any_publication"` — a work appears if any of its publications matches, and the displayed publication is the latest matching one. List items expose the latest `publication_id` and total `publications_count` for direct navigation to `/publications/{publication_id}`.
- **Publication-bearing invariant (do not regress).** Every work listing surfaces only works with at least one publication: the detail query hydrates the latest publication via `INNER JOIN publications p ON p.id = (SELECT MAX(p2.id) …)`, which drops publication-less works, so the id-selection query **must** agree or the page under-fills. The pure default browse in `_getWorksVitrine` (no filters, no `sort_by`) selects ids straight from the publications index — `SELECT DISTINCT work_id FROM publications ORDER BY work_id DESC LIMIT ? OFFSET ?` — instead of scanning `works`. Filtered/sorted paths keep their `works`-driven plans (the `cited_by_count`/`references_count`/`id` sorts run index-ordered with no publications join; `publication_year` joins for `MAX(p.year)`). Never force an unconditional `INNER JOIN publications + GROUP BY` on the sorted paths — it turns the indexed `cited_by_count` sort into a full scan + filesort and times out.
- The `limit` bound on `/works` and `/works/showcase` is **1..100** (`validateWorksQuery` in `src/routes/works.js`); `getWorks` and `getWorksVitrine` cap internally at `Math.min(limit, 100)`. `getWorks` forwards `result.meta`, so `/works` surfaces `meta.pagination_total_exact` like `/works/showcase`; the no-filter total is the non-exact estimate `ESTIMATED_WORKS_TOTAL` (distinct works carrying a publication). Cache keys: `works:list:v6:*` / `works:vitrine:v6:*`.
- Under the `manticore` backend, free-text `q` and the `author` / `subject` filters resolve through Manticore (`searchEngine.searchWorkIds`): `q` spans every text field, `author` → `@authors`, `subject` → `@subjects`, each with AND semantics; matching ids hydrate from MariaDB. The `venue_name` filter is the one text predicate that runs in MariaDB — it switches the venue JOIN to `INNER JOIN venues v` and matches `MATCH(v.name, v.abbreviated_name) AGAINST (? IN BOOLEAN MODE)` against `ft_venues_search`.
- Detail: `/works/{id}` embeds `publications[]` (full per-publication entries with their own `identifiers`, `venue`, `publisher`, `files`, `_links.self`, and an `is_primary` flag), `publications_total`, `publications_has_more`, and aggregated `identifiers` (union over every publication).
  - Live `files` JOIN. `/works/{id}` and `/publications/{id}` read the `files` base table directly: `_getCompleteWorkData` runs a bounded `SELECT … FROM files WHERE publication_id IN (…) LIMIT 500` (aliased to `mapFiles`'s shape — `file_format AS format`, `file_size AS size`, `file_role AS role`, `verification_status AS verification`, `download_count AS downloads`), groups by `publication_id`, and feeds `files_json` / `has_files` / `has_scimag_file` / `has_libgen_file` into the DTO. `/publications/{id}` uses `LIMIT 200`. On error the service logs and continues with an empty file list.
  - Work-level aggregations at the top level: `primary_publication_id`, a compact `primary_publication` block (id / doi / publication_year / publication_date / volume / issue / pages / venue / publisher / source / license / has_files / open_access / peer_reviewed / `_links.self`), convenience flags `publication_year` / `doi` / `open_access` / `peer_reviewed` / `has_files` / `venue` (from the primary), a `year_range` block (`earliest` / `latest`), a `languages[]` distinct list, and `summary_updated_at` (ISO of `works.metrics_last_updated`). Primary picker: latest `publication_year` DESC → `has_files` DESC → `publication_id` DESC.
  - `files[]` is a flat work-level aggregation capped at 50, sorted by role priority (MAIN > SUPPLEMENT > COVER > PREVIEW) then verification (VERIFIED first) then `publication_id` DESC. Each entry carries `publication_id`, `file_id`, `md5`, `format`, `size`, `pages`, `language`, `role`, `version`, `libgen_id`, `scimag_id`, `openacess_id`, `best_oa_url`, `verification`, `download_count`.
  - `file_summary` reports `files_returned`, `files_total`, `files_truncated`, `publications_with_files`, `total_download_count`, `best_oa_url`, `by_format`, `by_role`, plus `has_scimag` / `has_libgen` / `has_open_access` rollups.
  - `venues[]` is a distinct-venue roll-up (one entry per `venue_id`) carrying `publication_count` and `latest_year`, ordered by publication_count DESC, latest_year DESC.
  - `metrics` includes `publications_count`, `publications_with_files_count`, `publications_open_access_count`, `publications_peer_reviewed_count`, `distinct_venues_count`, `total_files_count`, `total_files_download_count`, `metrics_last_updated`.
  - Cache keys: `work:v5:{id}:c{0|1}:r{0|1}`; `/publications/{id}` uses `publication:{id}:v3:*`.

### Publications endpoints
- `/publications` and `/publications/{id}` are backed by `publications p INNER JOIN works w` + `LEFT JOIN venues v` + `LEFT JOIN organizations publisher`. Free-text (`q`) and the `author` / `subject` filters resolve matching work ids through Manticore (`searchEngine.fetchWorkIdsForFilters`), capped at `MANTICORE_PUBLICATIONS_WORK_CAP` (default 5000; `meta.fulltext_truncated` flags a hit), then filter `p.work_id IN (…)`. The `venue` filter matches through MariaDB `ft_venues_search` (and flips the venue join to `INNER JOIN`). Filter-only paths (`language`, `year_from`/`year_to`, `type`, `open_access`, `peer_reviewed`, `has_files`, `venue_id`, `publisher_id`, `work_id`, `doi`) hit B-tree indexes directly; `has_files` is enforced with `EXISTS (SELECT 1 FROM files f WHERE f.publication_id = p.id)`. `meta.engine` is `"Manticore"` whenever a full-text term participates, else `"MariaDB"`. List rows expose `source`, `license_url`, `license_version`; `venue` carries `type / issn / eissn / scopus_id / wikidata_id / openalex_id`; `publisher` hydrates from `organizations`. Detail responses embed `work`, `siblings[]`, `files[]`, optional `citations` / `references`.
- DOI resolution: `/{doi}`, `/doi.org/{doi}`, `/https://doi.org/{doi}` resolve a DOI to a publication via `publications.doi (UNIQUE)` and return the publication-shaped payload with the parent `work` embedded. The regex route is wired in `src/app.js`, handled by `publicationsController.getPublicationByDoi`.

### Venues endpoints
- `/venues`, `/venues/{id}`, `/venues/{id}/works`, `/venues/search`, `/venues/statistics` are backed by `venues v LEFT JOIN organizations pub ON pub.id = v.publisher_id`. Top subjects come from `venue_subjects + subjects` (ordered by `vs.score DESC, s.term ASC`, capped at 5 in list / 10 on detail). `/venues/search` runs a LIKE search across `v.name`, `v.abbreviated_name`, `v.issn`, `v.eissn`, `pub.name`.
- List `sortBy` accepts `id|name|type|impact_factor|works_count|h_index|cited_by_count|score|ranking|coverage_start_year|coverage_end_year|oldest|newest`. Default is `score` (`venues.total_score`) `DESC`; numeric/ranking fields default `DESC`, while `id`, `name`, `type`, `coverage_start_year`, `oldest` default `ASC` and `coverage_end_year`, `newest` default `DESC`. `oldest` / `newest` alias `coverage_start_year` / `coverage_end_year`. Rows with NULL coverage years are pushed to the tail regardless of direction. When the primary sort is not `score`/`ranking`, `COALESCE(v.total_score, 0) DESC` is appended as the tiebreaker, then `v.name ASC`. `/venues/search` orders by `COALESCE(v.total_score, 0) DESC, v.name ASC`. `meta.sort` reports the effective `{ by, order }`.
- Coverage year filters on `/venues`: `coverage_from` / `coverage_to` bound the range; `coverage_start_from` / `coverage_start_to` / `coverage_end_from` / `coverage_end_to` bound the individual endpoints; `active_in_year` keeps venues whose coverage range encloses the year.
- Payload blocks:
  - `identifiers`: `issn`, `eissn`, `scopus_id`, `wikidata_id`, `openalex_id`, `scielo_id` (not repeated at the top level).
  - `indexing`: `is_in_doaj`, `is_in_scielo`, `is_indexed_in_scopus`, `validation_status`.
  - `metrics`: `impact_factor`, `citescore`, `sjr`, `snip`, `h_index`, `i10_index`, `two_yr_mean_citedness`.
  - `ranking`: `score` (= `venues.total_score`), `components.{subject|oa|impact|llm}` (the four additive components sum exactly to `score`), `llm.{relevance|justification}`. `impact` maps to `venues.impact_score`.
- A single `subjects[]` array carries the top subjects (capped at 10 on detail, `{subject_id, term, score, vocabulary, lang}`).
- Core surface: `publisher`, `language` (from `venues.lang`, ISO 639-1), `coverage_start_year` / `coverage_end_year`, `works_count`, `cited_by_count`, `open_access`, `aggregation_type`, `country_code`, `homepage_url`. Detail additionally embeds `publication_summary` (`first_publication_year` / `latest_publication_year`, `total_works_count`, `open_access_works_count`, derived `open_access_percentage` — computed from the per-year aggregation, null when no yearly data — and `publication_trend`), `yearly_stats`, `top_authors`, `top_publications`, `recent_works`, and the timestamps (`created_at`, `updated_at`, `last_validated_at`, `summary_updated_at`).
- Include flags on detail: `include_subjects`, `include_yearly`, `include_top_authors`, `include_recent_works` (all default `true`).
- Cache keys: list `venues:list:v7:...`, detail `venue:v6:{id}:{include_flags}`, search `venues:search:v5:...`. `/venues/search` is an implementation alias of the `venues?search=` listing (same LIKE over `name`/`abbreviated_name`/`issn`/`eissn`/publisher, same `COALESCE(total_score,0) DESC, name ASC` sort) that restores the search `meta` (`source`+`query`, no `sort`). `mag_id` is never exposed.
- The listing `meta.source` reports `"venues"`.

### Institutions endpoints
- `/institutions`, `/institutions/{id}`, `/institutions/{id}/works`, `/institutions/{id}/funded-works` are backed by the `organizations` base table. Division of labour: **whatever the DB stores, the API presents verbatim and never recomputes** — the org metric columns (`publication_count`/`researcher_count`/`total_citations`/`h_index`/`i10_index`/`2yr_mean_citedness`) are the source of truth. **Whatever is useful but the DB does not store, the API derives internally** — the corpus year range (`first/latest_publication_year`), production-by-type, yearly trend, top authors, recent works are computed from the affiliated-works corpus, each bounded by `max_statement_time`, cached, gated behind an include flag, and degrading gracefully.
- List shape: `{ id, name, type, openalex_type, status, acronyms[], location{country_code,city}, identifiers{ror_id,grid_id,wikidata_id,openalex_id,url}, metrics{works_count,researchers_count,total_citations,h_index,i10_index,two_yr_mean_citedness}, created_at, updated_at, _links.self }`. Identifiers are not duplicated at the top level. `relevance` appears only on search responses. The open-access surface is not exposed on `/institutions` (the stored `open_access_works_count` scope-mismatches `publication_count`, so a derived percentage could exceed 100%); `/metrics/institutions` still surfaces the raw count.
- Detail adds `names{acronyms,alternative_names,aliases_count}` (`aliases_count` = `acronyms.length + alternative_names.length`), `metrics.first_publication_year`/`latest_publication_year` (bounded corpus query), `funding_role{funded_works_count,grants_count}`, `production_summary{by_work_type,publication_trend}`, `relationships{parents,children,related,*_count}` (from `organization_relationships`), `top_authors[]`, `recent_works[]`, `_links{self,works,funded_works}`. Include flags (default `true`): `include_production`, `include_authors`, `include_works`, `include_relationships`.
- Browse is **activity-based**: every list/search query is anchored on `o.publication_count > 0`. List filters: `search`/`q` (FULLTEXT `ft_organizations_name` ∪ exact acronym match `JSON_CONTAINS(o.acronyms, JSON_QUOTE(:qUpper))`), `type`, `openalex_type`, `country`/`country_code` (ISO-2), `status`, `has_ror`, `works_min`/`works_max`, `researchers_min`, `cited_by_min`/`cited_by_max` (against `total_citations`), `h_index_min`. Sort: `sort_by` ∈ `works_count`(default)`|researchers_count|citations|h_index|i10_index|name|id|created_at|updated_at|relevance`; `sort_order` ASC/DESC (numeric default DESC, name/id ASC). Search default sort is `relevance`, ordered `acronym_exact DESC, publication_count DESC, MATCH-relevance DESC`. `meta.sort{by,order}` and `meta.pagination_total_exact` are always reported; the count runs under a 2.5 s budget. Detail-by-id resolves any organization regardless of activity.
- `/institutions/{id}/works` lists works whose authorships carry this org as `affiliation_id`; `/institutions/{id}/funded-works` lists works financed through `funding.funder_id` (each row carries `grant_number`) — the only useful surface for pure FUNDER orgs. Both honour the standard work sort contract (`cited_by_count|references_count|publication_year|id`) plus `type`/`language`/`year_from`/`year_to`/`open_access`/`peer_reviewed`/`cited_by_min`/`cited_by_max`, expose `meta.match_mode` (`affiliation` / `funder`), and reuse the shared `formatAffiliatedWork` DTO.
- Cache keys: list `organizations:v5:...`, detail `organization:v4:{id}:{flags}`, works `organization:{id}:works:v2:...`, funded-works `organization:{id}:funded:v1:...`, metrics `metrics:institutions:v2:...`.

### Search endpoints
- `/search/works`, `/search/advanced`: `q` is optional; filter-only queries (e.g. `venue=mana`) are supported. The `author`/`subject` metadata-filter AND semantics apply, resolved through Manticore (`@authors` / `@subjects`).
- `/search/global`, `/search/persons`, `/search/autocomplete`, `/search/popular`, `/search/health`.
- `/search/autocomplete` honours the `{ suggestions, type, count, query, generated_at }` envelope. It discovers candidate work ids through Manticore (`searchEngine.fetchWorkIdsForMatch`), then derives title / author / venue suggestions via `works` / `authorships+persons` / `publications+venues` lookups. It returns an empty suggestions list if the full-text path fails — it never surfaces `{ error: … }` inside a `status: success` payload.

### Metrics and dashboard
- `/metrics/annual` (publications + works by year), `/metrics/venues` (by `venues.works_count`), `/metrics/institutions` (ranks `organizations` by stored `publication_count`, restricted to `> 0`; surfaces `total_works`/`total_citations`/`unique_researchers`/`open_access_works_count`/`h_index` from stored columns, first/last publication year from a page-scoped `authorships`+`publications` join), `/metrics/persons` (persons table directly, ordered by `total_works DESC, total_citations DESC`), `/metrics/collaborations` (authorships self-join over the top 2000 persons by `total_works`).
- Dashboard (access key required): `/dashboard/overview`, `/dashboard/performance`, `/dashboard/search-trends`, `/dashboard/alerts`. MariaDB-side activity only.

### Subjects endpoints
- The `/subjects` root collection listing is disabled (see Endpoint inventory); the nested endpoints stay active. Term search runs against `ft_subjects_term`.
- Every subject `works_count` is read from the denormalized `subjects.total_works` column (never a request-time `work_subjects` join): `/subjects/statistics`, `/subjects/{id}`, `/subjects/{id}/children`, and `/subjects/{id}/hierarchy` all source it from the stored value, so even the largest subjects resolve in milliseconds. `avg_relevance_score` on the detail is `null` (the underlying `work_subjects.relevance_score` is a uniform placeholder, so no scan is run to average it).
- `/subjects/statistics` returns structural counts (total / root / child / typed subject counts, per-vocabulary `vocabulary_distribution` with `works_count`) plus the work-linkage stats `subjects_with_works`, `total_work_subject_relations` (= `SUM(subjects.total_works)`), and a `top_subjects` list (top 20 by `total_works`, each with `subject_type`). `data.meta.work_linkage_available` is `true` (`source: subjects.total_works`). Cache key `subjects:statistics:v3`.
- `/subjects/{id}/children` orders children by `total_works DESC, term ASC` and carries per-child `works_count` + `children_count`; `/subjects/{id}/hierarchy` walks `parent_id` to the root, each node carrying its `works_count`.

## Search Engine
- **Manticore Search** (25.0.0, SphinxQL on `127.0.0.1:9306`, accessed via `mysql2` with `database: 'Manticore'`, `ssl: false`) powers full-text search for `works` and `persons`. `searchEngine.isEnabled()` is `SEARCH_BACKEND === 'manticore'`; the runtime pins `manticore`, mandatory for works. Works/publications/autocomplete/persons services resolve matches + relevance via Manticore (`src/services/searchEngine.service.js` over `src/config/manticore.js`), then hydrate rows from MariaDB by id. The venue filter still resolves through MariaDB `ft_venues_search`.
- **Index design** (`config/manticore.conf`): path mode (no `data_dir`), plain `works_main`/`works_delta` + distributed `works`, and `persons_main`/`persons_delta` + distributed `persons`. The `works` index holds full-text fields title, subtitle, abstract, authors, subjects, venue — authors/subjects/venue concatenated at index time via `sql_joined_field` over `authorships`+`persons`, `work_subjects`+`subjects`, `publications`+`venues` — plus attributes `language`, `citation_count`, `reference_count`, `min_year`/`max_year`, and MVAs `type_codes`/`years`/`oa_flags`/`pr_flags`. `type_codes` carries the 1-based enum ordinal of each `publications.type` (`ARTICLE=1 … OTHER=12`), sourced per-publication so the `type` filter matches a work when any of its publications is of that type; `searchEngine.service.js` maps the filter string via `WORK_TYPE_CODES`. Free-text `q` spans every text field `@(title,subtitle,abstract,authors,subjects,venue)`; explicit filters stay scoped — `author` → `@authors`, `subject` → `@subjects`, `venue_name` → `@venue`. `/publications` free-text resolves work ids capped at `MANTICORE_PUBLICATIONS_WORK_CAP` (default 5000).
- **Relevance ranking**: when the sort is relevance (the default), works use `expr('sum(lcs*user_weight)*1000 + bm25 + min(citation_count,1000)*50')` with `field_weights=(title=10, subtitle=4, abstract=2, authors=6, subjects=4, venue=4)`; persons use `expr('sum(lcs*user_weight)*1000 + bm25 + min(total_works,500)*20')` with `field_weights=(preferred_name=10, family_name=6, given_names=4)`. Explicit attribute sorts (`cited_by_count` / `references_count` / `publication_year` / `id`) skip the expression ranker and order by the attribute directly. `COUNT(*)` totals are exact.
- **Morphology** is enabled on the `works` content fields only: `morphology = libstemmer_pt, libstemmer_en` with `morphology_skip_fields = authors, venue`, so title/subtitle/abstract/subjects collapse inflected variants while author and venue names stay verbatim. `dict=keywords` + `min_prefix_len=3` + morphology forces `index_exact_words=1`, so an `=term` query matches the un-stemmed surface form exactly. `persons_*` is unstemmed. Morphology is applied at index time, so toggling it requires an operator rebuild.
- **Build/refresh is operator-side** (the API never writes the index): `scripts/manticore/render-config.sh` deploys the config with the DB password from `/etc/node-backend.env`; `scripts/manticore/reindex.sh {init|delta|main}` builds/rotates via `indexer`. Delta = works/persons with `updated_at` in the last 48h; each delta table declares `killlist_target = <main>:kl` so its `sql_query_killlist` ids suppress the stale main copy. Cron rebuilds delta every few minutes and main nightly. The `indexer` `dlopen`s `libmysqlclient.so.21`; it must be symlinked to `libmysqlclient.so.24`.
- **No MariaDB works fallback.** `venues`/`persons`/`subjects`/`organizations` keep their FULLTEXT indexes; `works` has none. The dead `else` (mariadb) branches that used to MATCH the dropped `works` search columns were removed from `works.service.js` / `publications.service.js` / `autocomplete.service.js` / `search.js` (`/search/health`); the Manticore path is now unconditional, so `SEARCH_BACKEND` must stay `manticore` (the runtime pins it). The live MariaDB fulltext that remains is the venue filter (`ft_venues_search`) and the persons short-query LIKE fallback — both intentional.
